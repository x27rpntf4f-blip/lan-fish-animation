# FishMesh 分布式多屏协同平台设计规格

日期：2026-07-26  
状态：待用户书面审阅  
演进来源：局域网多屏联动游鱼动画系统

## 1. 目标与定位

FishMesh 将现有多屏游鱼课程项目深化为一个跨平台、可复用、可验证的局域网分布式状态迁移平台。项目重点展示分布式系统与网络工程能力，游鱼动画保留为首个可视化演示应用，而不再承担协议、成员管理和拓扑逻辑。

目标平台为 Windows、macOS 和 Linux。项目保留 Python 技术栈并渐进重构，核心网络运行时采用 `asyncio`。系统既支持三台及以上真实设备组网，也支持在一台电脑上通过多进程复现实验。

## 2. 设计原则

1. 协议与 pygame 解耦；网络核心不依赖具体演示应用。
2. 成员关系、屏幕布局和业务实体所有权分别建模。
3. 根据消息价值选择可靠性语义，不将全部 UDP 流量改造成 TCP。
4. 所有协议处理都必须有边界检查，异常报文不能使节点退出。
5. 结论由可重复实验支撑，明确区分模拟数据和真实设备数据。
6. 每个里程碑都形成可运行、可测试、可展示的独立版本。

## 3. 系统架构

### 3.1 `fishmesh-core`

与应用无关的协议与领域模型：

- 版本化二进制协议信封；
- 节点身份、会话身份和消息序列；
- ACK、超时重传、去重和可靠分片；
- 成员事件、布局模型和实体迁移状态机；
- 纯逻辑组件，不直接依赖 pygame。

### 3.2 `fishmesh-runtime`

每个节点运行的异步分布式运行时：

- `asyncio` UDP 端点和有界发送队列；
- 节点发现、成员探测和故障状态维护；
- 控制面事件总线；
- 二维邻接路由和点对点状态迁移；
- 结构化日志和指标采集；
- 面向应用层的稳定 API。

### 3.3 `fish-demo`

现有游鱼项目演进形成的演示应用：

- pygame 负责渲染、输入和本地业务状态；
- 通过 runtime API 发布迁移请求并接收远端实体；
- 不直接调用 Socket，不解析协议帧；
- 保留背景、精灵、音频和配置等现有视觉功能。

### 3.4 `cluster-simulator`

单机实验与故障注入工具：

- 启动多个独立节点进程；
- 使用固定随机种子复现实验；
- 注入延迟、抖动、丢包、重复、乱序、分区和进程退出；
- 读取场景文件并自动生成结构化结果。

### 3.5 `monitor-dashboard`

监控与演示界面：

- 实时节点和二维拓扑；
- 延迟、吞吐、重传、丢包、队列和迁移指标；
- 节点生命周期和故障注入时间线；
- 实验结果导出为 JSON、CSV 和图表。

## 4. 协议设计

### 4.1 协议信封

协议 V2 的统一帧至少包含：

- magic 和协议版本；
- 消息类型与标志位；
- 稳定 `node_uuid`；
- 每次进程启动生成的 `session_id`；
- 消息 `sequence`；
- 负载长度；
- 完整性校验值；
- 版本对应的负载。

未知版本、未知类型、长度不匹配、校验失败和字段越界均返回可观测错误，不进入业务处理。

### 4.2 可靠性分级

#### 尽力而为

适用于发现、心跳和高频指标。消息允许丢失，不做逐包重传，由下一周期自然修复。

#### 至少一次传输加业务去重

适用于状态迁移、布局修改和重要控制消息。发送方维护超时与重试；接收方通过操作 ID 去重，重复请求只返回原结果，不重复执行副作用。

#### 可靠分片传输

适用于精灵和其他大资源。包含资源清单、分片编号、选择确认、窗口控制和最终内容校验。接收方仅请求缺失分片，并对资源名称和落盘路径做严格校验。

### 4.3 超时、重试与背压

- 初版使用可配置 RTO、最大重试次数和操作 TTL；
- 后续基于采样 RTT 研究自适应 RTO；
- 发送队列必须有界并区分消息优先级；
- 控制消息不得被大资源传输饿死；
- 动画高频更新可降采样，可靠控制消息不可静默丢弃；
- 达到重试上限后产生显式失败事件并触发业务回滚。

## 5. 成员关系与故障检测

节点使用持久化 UUID 标识，不能使用 IP 排序位置或临时 host_id 作为永久身份。每次进程启动生成新的 session，旧会话报文不能刷新新会话的存活状态。

成员状态为：

`UNKNOWN -> JOINING -> ALIVE -> SUSPECT -> DEAD`

初版采用可配置心跳和怀疑超时；后续实现 SWIM-inspired 直接探测、间接探测和成员变更 piggyback，并研究 Phi accrual failure detector 在不同网络条件下的误判表现。

成员信息采用最终一致模型，不引入全局强一致或 Raft。成员变更应在限定时间内传播并收敛，收敛过程必须可观测。

## 6. 二维屏幕拓扑

成员表只表示节点是否在线，屏幕布局单独表示物理空间。每个显示节点声明：

- 屏幕尺寸和缩放信息；
- 全局画布中的矩形位置；
- 节点能力和可用出口；
- 当前布局 epoch 和布局哈希。

邻接关系由矩形边界和重叠区间推导，支持不同分辨率、DPI和垂直偏移。实体跨越边缘时，根据出口方向和交叠区域选择目标节点，并把局部坐标转换到全局坐标后再映射到目标局部坐标。

布局修改由一个会话协调者排序并发布。协调者只负责低频布局控制，不参与业务状态迁移；协调者失效后按稳定规则重新选举。首版不宣称该机制提供强一致共识，检测到相同 epoch 的布局哈希冲突时必须暂停跨屏迁移并显式报警。

## 7. 实体所有权与迁移

每个实体使用稳定 UUID，不再把动态主机编号编码进实体 ID。每次迁移生成唯一 `migration_id`，并携带单调增加的 `owner_epoch`。

迁移状态为：

`ACTIVE_SOURCE -> PREPARING -> IN_FLIGHT -> ACTIVE_TARGET`

失败路径为：

`PREPARING | IN_FLIGHT -> ROLLBACK_SOURCE`

流程如下：

1. 源节点冻结实体迁移快照，但继续保留实体所有权。
2. 源节点向目标节点可靠发送迁移请求。
3. 目标节点校验 owner epoch，按 migration ID 去重并恢复实体。
4. 目标节点记录结果后返回 ACK。
5. 源节点收到提交确认后删除本地实体。
6. 超时、拒绝或目标故障时，源节点恢复本地活动状态。

该设计提供至少一次消息交付加幂等业务执行，不声称在任意崩溃模型下实现严格 exactly-once。后续可增加邻居低频检查点，研究节点突然死亡时的恢复点目标和状态损失范围。

## 8. 可观测性

核心事件使用结构化日志，至少包含 timestamp、node UUID、session、peer、message type、sequence、operation ID、result 和 duration。

核心指标包括：

- 节点数量与成员状态；
- RTT、P50/P95/P99 延迟；
- 吞吐、原始丢包、重传和重复消息；
- 发送队列长度与丢弃策略；
- 迁移成功率、回滚数和完成时间；
- 成员变更传播时间与拓扑收敛时间；
- CPU、内存和渲染帧率。

监控不能改变协议语义；关闭监控后核心系统仍可运行。

## 9. 测试与实验

### 9.1 单元测试

覆盖协议编解码、边界检查、CRC、序列回绕、去重缓存、超时重试、布局映射和所有权状态机。

### 9.2 性质与模糊测试

- 任意合法消息编码后再解码得到等价对象；
- 任意截断、随机或字段畸形报文不会使节点崩溃；
- 同一 migration ID 执行任意次数最多产生一个目标实体；
- 迁移未提交时源实体不能被永久删除。

### 9.3 多进程集成测试

验证节点加入、离开、重启、网络分区、乱序、丢包、重复、状态迁移和资源断点续传。测试场景使用固定随机种子并自动判定结果。

### 9.4 三机跨平台实验

使用 Windows、macOS 和 Linux 混合节点验证真实组网。所有报告注明设备、系统、网络、版本、时间和样本数，不能把模拟结果表述为真实设备结果。

### 9.5 初始质量目标

- 三平台持续集成通过；
- 核心模块测试覆盖率目标不低于 85%；
- 在定义清楚的 10% 模拟丢包场景中，可靠消息最终交付率目标不低于 99.9%；
- 故障检测和拓扑收敛时间由场景配置给出并自动验证；
- 实验结果可由固定种子复现。

性能阈值必须在 M0 基线完成后校准，本节目标不是未经测量的性能承诺。

## 10. 跨平台与工程化

- 使用 `pyproject.toml` 管理Python版本、依赖和开发工具；
- 采用 `src/` 包布局，运行时代码和演示应用分包；
- 使用 pytest、类型检查和代码质量检查；
- Windows、macOS、Linux 持续集成；
- 配置中不允许保留个人绝对路径；
- 核心逻辑不直接依赖系统专有 API；
- Windows DPI 等平台适配放在演示应用的适配层；
- 提供开发安装、普通运行、单机模拟和多机部署文档。

## 11. 长期里程碑

### M0：封存基线

保留现有应用为 legacy demo，记录功能、已知缺陷、启动方式和性能数据。

### M1：工程重构

建立包结构、项目元数据、测试、类型检查、结构化日志和三平台 CI；拆分现有主循环，但保持用户可见功能不变。

### M2：协议 V2

实现独立 core、版本帧、稳定身份、边界检查、ACK、重传、去重、可靠分片、有界队列和旧协议兼容适配层。

### M3：集群运行时

实现成员管理、二维布局、动态邻接、实体所有权迁移和失败回滚，使 Fish Demo 只通过 runtime API 访问网络。

### M4：实验平台

实现多进程编排、故障注入、实时监控、自动结果导出和一条命令运行的五节点实验。

### M5：作品发布

提供跨平台安装方式、设计文档、协议说明、实验报告、演示视频、示例插件和版本发布。

### M6+：研究扩展

一次只选择一个具有对照实验的问题，例如 Phi 故障检测、轻量状态副本、自适应 RTO 或安全握手。每项研究必须包含基线、变量、结果和限制。

## 12. 明确不做

首轮长期设计不包含：

- Raft 或通用分布式共识系统；
- 公网 NAT 穿透和中继服务器；
- 与核心目标无关的大量 UI 功能；
- 为展示多语言而重写网络核心；
- 未经实验支撑的“绝对可靠”“零丢失”或“严格 exactly-once”承诺。

## 13. 复试作品成果

最终作品至少包括：

1. 可公开阅读的源码和提交历史；
2. 架构、协议、状态机和实验方法文档；
3. 三平台可运行的 Fish Demo；
4. 单机五节点一键实验；
5. 三机真实组网和故障恢复演示；
6. JSON/CSV 实验数据与图表；
7. 约 90 秒的核心演示视频；
8. 能诚实解释设计取舍、失败模型和已知限制的答辩材料。

推荐项目叙事：从一个 UDP 多屏游鱼课设出发，识别节点身份、消息可靠性和测试复现中的系统性问题，逐步将其重构为跨平台的局域网分布式状态迁移框架，并通过真实设备与可控模拟实验量化验证设计。
